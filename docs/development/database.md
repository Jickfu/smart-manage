# 数据库开发

## 权威来源

数据库结构和必要初始化数据只由所属模块的 Flyway 迁移定义。平台位于 `smart-manage-server/platform/src/main/resources/db/platform/migration`，可选 DEMO 位于 `smart-manage-server/domains/demo/src/main/resources/db/demo/migration`。构建后资源随普通 JAR 交付，不再使用根目录 `db/business` 或复制迁移目录。

当前尚未正式发布，本次直接重组 V1/V2 基线，不兼容旧开发库，不自动修改历史或删除数据。新安装使用空库；已有个人开发库是否重建由使用者明确决定。正式发布后的规则见下文。

## 平台与领域迁移链

| 项目 | 平台 | 可选领域（DEMO 示例） |
| --- | --- | --- |
| 类路径 | `classpath:db/platform/migration` | `classpath:db/demo/migration` |
| 历史表 | `flyway_schema_history` | `flyway_demo_schema_history` |
| 版本 | V1 结构、V2 必要数据，后续递增 | 独立从 V1 开始 |
| 启用 | 默认 | Maven `with-demo` 装配进最终包 |

领域 JAR 的 `META-INF/smart-manage/migration.properties` 声明 `id`、`location`、`table`、`minimum-platform-version`。平台通用配置发现声明，保留 Boot 的平台 Flyway Bean 与初始化依赖，先执行平台，再检查领域最低平台版本并执行领域迁移。已声明领域的配置无效、目录缺失、空链、重名或迁移失败均拒绝启动，不自动跳过；装配测试确认选入的领域声明确实存在。

当前各可选领域只依赖平台，按标识稳定排序，不支持领域依赖图。平台不得声明采购专属目录、业务键或迁移。每条链使用独立历史表和版本空间，不能合并到同一 `spring.flyway.locations`。

平台完成后 schema 已非空，领域首次启动只在自己的历史表登记版本 0，随后执行全部 V1+。版本 0 不得作为实际 SQL 版本。各链校验 checksum 和命名，禁用乱序、自动 clean 和 repair；平台成功、领域失败不会回滚已经提交的平台变更。

## 对象所有权与二次开发

平台拥有系统表与自身必要目录数据；可选领域拥有自身表、Feature、权限、菜单、应用、编号规则及相关测试和文档。扩展使用独立稳定编码和主键，不覆盖平台行，不以忽略冲突 SQL 掩盖不同语义。

删除后端及前端领域目录只能裁剪源码与新安装产物，不能卸载已经初始化的数据库；已有数据的卸载须另行设计。独立版本链也不能消除对象冲突或应用版本兼容问题。

## 必要数据与开发 fixtures

平台 V2 默认只保留一个公司、管理员及关联和运行所需的系统目录、规则。管理员密码为空的不可登录标记，由首次启动的外部配置初始化，规则见[环境与配置](./configuration.md#管理员首次初始化)。

多部门开发数据位于根目录 `dev-support/fixtures/multiple-departments.sql`，仅在明确需要时由开发者向自己的测试库显式导入，不随任何 profile、首次启动或领域装配自动执行。领域自有 fixtures 应放在 `domains/{领域}/fixtures`。当前 DEMO 不含演示单据；选择它只创建必要结构和目录数据。

## 正式发布与升级规则

首次安装在空数据库上执行 V1（数据库结构）和 V2（必要初始化数据）。正式发布以 V2 完成状态作为后续升级测试起点；后续版本必须保留已发布迁移并提供向前升级路径。

1. 已进入共享、发布或长期使用环境的迁移内容和文件名冻结。数据库修复新增版本，不回填到 V1/V2，不用 repair 改 checksum 掩盖实际差异。
2. 一个迁移表达一个完整数据库变更；没有数据库变化的代码修复不新增 SQL。只在个人可重建库执行过的未发布草稿可以在发布前整理，并重新验证空库。
3. 公共自动升级默认保留用户数据，开发库清空、日志清理和环境重置放在自动扫描目录之外。破坏性变更必须提供明确升级步骤、备份恢复验证和支持范围。
4. 发布说明列出支持的起始平台版本、业务最低平台版本、对象变化、停机要求和失败恢复方式。发布前验证空库安装、每个受支持起点的带数据升级及再次启动无重复执行；新增迁移补充对应真实数据回归，不能仅验证 SQL 可执行。
5. 生产升级先在副本演练并验证备份可恢复，再按发布要求停止旧实例，由指定实例完成迁移后启动其他实例。各历史表的 Flyway 锁不代表双链构成全局事务，也不保证混合版本滚动发布兼容。
6. 平台成功、业务失败时平台变更仍已提交。核实数据库与两张历史表后恢复业务链；事务 SQL 失败只有在确认回滚后才可修正尚未发布且未成功执行的脚本。已发布脚本不能任意覆盖，非事务副作用需核对并提供受控恢复方案。不得关闭业务链、开启乱序或自动 repair 绕过失败。
7. 回退应用代码不等于回退数据库；按已验证兼容版本启动或恢复完整备份，不提供自动 down migration。

迁移文件较多本身不是缺陷。将来确有新安装耗时问题时可单独评估累计基线，同时验证新安装和已有库升级；已发布的版本迁移不得删除。

## SQL 约定

- Java 查询条件使用 MyBatis-Plus `LambdaQueryWrapper` 和方法引用，禁止裸表名、字段名字符串。
- XML Mapper 的主表别名使用 `a`，JOIN 表按出现顺序使用 `b`、`c`、`d`。
- 主从表通过明细表 `parent_id` 关联，不使用数据库级联删除。
- 客户端和数据库写入使用 UTF-8，不依赖 GBK 写入。

## 表和字段备注

业务对象的长期说明统一使用 `description`；`remark` 只用于单据明细、执行记录或审计记录等单次业务附言。两者语义无法明确区分时只保留 `description`，禁止在同一对象中并存同义字段。

创建表时必须使用 PostgreSQL `COMMENT ON` 添加表备注和字段备注。

| 字段 | 统一备注 |
| --- | --- |
| `id` | ID |
| `number` | 编码 |
| `name` | 名称 |
| `biz_date` | 业务日期 |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |
| `create_user` | 创建人 |
| `update_user` | 修改人 |

其他字段根据业务含义填写简体中文备注。

## 稳定业务编码

被 URL、外部集成或跨记录引用的 `number` 属于稳定业务身份，创建后不得修改，并由数据库唯一约束承担并发写入的最终保障。菜单编码用于 `app + entry` 浏览器启动入口，因此 `t_sys_menu` 使用 `(app_id, number)` 应用内唯一约束；不同应用可以使用相同菜单编码，解析时必须同时提供应用编码。

## 日志分区

系统日志使用 PostgreSQL 原生月度范围分区，具体父表、命名、生命周期任务和新增日志检查项见[日志数据生命周期](../architecture/log-lifecycle.md)。分区仍属于数据库结构，只能通过新增 Flyway 迁移创建或扩展；禁止由请求参数、任务参数或普通业务代码指定任意表名执行 DDL。

## 本地排障

PostgreSQL 客户端路径取决于安装时的选择。Windows 常见安装位置包括：

```text
D:\Program Files\PostgreSQL\16\bin
C:\Program Files\PostgreSQL\16\bin
```

Flyway 空库验证默认使用 PATH 中的 PostgreSQL Client 16。无法加入 PATH 时，使用 `-PsqlPath` 参数传入 `psql.exe` 的完整路径；客户端主版本必须和当前 CI 的 PostgreSQL 16 基线保持一致。

执行 SQL 时必须使用当前环境已有的安全凭据方式，例如临时 `PGPASSWORD` 或受控连接配置。禁止把密码写入脚本、代码、文档、提交记录或回复。

只有确认 Windows 终端输出乱码时，才临时调整查询输出的客户端编码；数据库写入始终使用 UTF-8。

## 验证

迁移变更必须执行[Flyway 空库验证](./verification.md#flyway-空库验证)，并确认后端测试或编译通过。
