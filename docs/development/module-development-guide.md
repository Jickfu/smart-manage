# 模块开发指南

本指南用于新增或显著扩展 Smart Manage 业务模块。它负责把仓库架构约束转化为可执行的开发流程；根目录和前后端 `AGENTS.md` 仍是强制规则来源，领域文档仍是具体业务语义来源。

小范围缺陷修复、纯重命名或不改变模块边界的局部调整不要求完整执行本流程，但仍必须遵守相关 `AGENTS.md` 和验证规则。

## 1. 实现前基线

在写代码前必须从仓库确认并记录以下内容：

| 项目 | 必须明确的结果 |
| --- | --- |
| 需求边界 | 本次实现什么、明确不实现什么、可验证的完成标准 |
| 模块类型 | 业务聚合、主数据、配置、查询记录、监控/控制台或公共能力 |
| 归属 | `{领域}/{应用}/{模块}`、是否属于系统内核、允许依赖的方向 |
| 稳定身份 | `featureKey`、页面键、权限码、业务资源类型、编号引用键等 |
| 页面形态 | `LIST + EDIT`、单独 `CUSTOM`，或确有依据的其他组合 |
| 状态与命令 | 保存、提交、启停、封存、取消、重试等命令及其最小参数 |
| 数据边界 | 组织归属、对象级访问、敏感字段、凭据、并发版本和保留周期 |
| 参考实现 | 从模块样板目录选择的后端、前端和测试样板；不能只凭记忆实现 |
| 验证 | 编译、测试、静态检查、生成器、迁移和必要的浏览器验收 |

如果其中任一未明确项会改变架构方向、数据安全、外部状态或形成明显不同的产品结果，必须先询问；其余内容优先通过代码、迁移和当前文档自行核实。

## 2. 模块分类和默认形态

### 2.1 业务聚合

具有独立业务身份、状态流转或主从数据的单据属于业务聚合。默认采用：

- 后端公开 `*Service` 加包级 `*TxService`；
- Entity、Form、VO、Mapper 和纯字段 Converter；
- `listPage`、`detail`、`createNewData`、`save`、`submit`、`delete` 等标准语义；
- 前端 `LIST + EDIT`、Query Key Factory、领域 Mutation 和页签生命周期；
- 可修改聚合使用 `version`，主从数据在同一事务内写入；
- 同时执行[业务聚合检查清单](./business-aggregate-checklist.md)。

### 2.2 主数据或独立配置

具有独立编码、列表、新增、编辑和详情语义的主数据或配置，默认采用独立 `LIST + EDIT` 页面。禁止为了少建一个页面，把列表与编辑表单拼进同一个 `CUSTOM` 页面。

配置中的密码、令牌、私钥或授权码不属于普通参数：必须遵守敏感配置和数据脱敏规范，详情只返回“是否已配置”等安全状态。

### 2.3 查询记录

日志、发送记录、执行记录等不可随意修改的事实数据，通常采用 `LIST` 加独立只读详情页签。详情不能用 Drawer 代替工作台页面；重新发送、取消等动作应建立专用命令，不能改写历史记录。

### 2.4 监控和控制台

只有布局、实时交互或信息密度确实无法由通用列表/编辑模型表达时才使用 `CUSTOM`。CUSTOM 不是绕过页面生命周期、权限、查询状态或视觉规范的捷径。

### 2.5 公共能力

出现第二个真实使用方并且语义稳定后，才考虑提取领域或应用 `common` 能力。公共层不得吸收具体业务语义，也不得通过扫描、命名或路径推断稳定业务身份。

## 3. 后端实现顺序

1. 确认领域文档、安全边界、数据归属和状态机。
2. 设计新增 Flyway 迁移；系统内置 Feature、权限、菜单和必要初始化数据一并通过迁移维护。
3. 定义 Entity、Form、VO 和权限常量，明确 ID、`version`、引用对象及敏感字段的 JSON 边界。
4. 建立 Mapper 和纯字段 Converter；关联查询应批量加载或由 MyBatis 直接投影。
5. 建立唯一公开 `*Service`，负责查询、命令入口、权限补充校验、业务组装和 `@BizLog`。
6. 将事务写入放入同模块包级 `*TxService`，事务内重新校验存在性、状态、版本和唯一性。
7. Controller 只依赖公开 Service，统一使用 `Result<T>`，权限注解引用模块权限常量。
8. 为状态、事务、并发、安全、外部副作用和架构边界补充风险驱动测试。

### 后端关键决策

- `save` 只保存新增或暂存修改；`submit` 保存完整聚合并推进状态。
- 启用、停用、封存等独立状态必须使用专用命令，只接收 ID、并发版本和目标状态等最小参数；不得混入保存 Form。
- 详情中的实体引用返回引用对象，默认包含 `id`、`number`、`name`；保存只提交外键 ID。
- 外部 HTTP、SMTP、对象存储等副作用原则上不在数据库事务中执行，并定义超时、失败和补偿语义。
- 具有独立业务身份的主数据和单据使用 `number`；通用说明性字段使用 `description`。

## 4. 前端实现顺序

1. 根据模块类型选择 `LIST + EDIT` 或 `CUSTOM`，并从[模块样板目录](./module-pattern-catalog.md)选择最接近的页面。
2. 定义 `types.ts`、`api.ts`、`permissions.ts`、`queryKeys.ts` 和 `pageRegistration.ts`；前端 ID 一律为 `string`。
3. 页面注册显式声明稳定 `featureKey`，同一功能的 LIST、EDIT、CUSTOM 页面共享该身份。
4. 列表优先使用 `ListPage` 和 `useListPageQuery`；编辑优先使用 `EditPage`；实体引用优先复用或新增 `use*RefSelector`。
5. 领域页面负责状态流转、Mutation、缓存失效、详情回显和页签替换，不在页面壳层重复实现通用 loading 与错误提示。
6. 完成列表选择、命令启用条件、编辑/查看模式、脏数据保护和首次保存后的临时页签替换。
7. 按同类页面完成视觉核对，再执行生成器、静态检查、测试和构建。

### 列表和命令

- 默认使用复选框；单记录命令在恰好选中一条时启用。只有业务语义天然互斥且无法用命令启用条件表达时才使用单选。
- 默认不增加“操作”列。编辑或查看优先使用可点击的 `number` 等稳定业务标识，其他命令集中在页面操作区。
- 可由 `columnFeatures` 表达的字段筛选、枚举筛选和排序不得通过 `filterContent` 重复实现。
- 至少保留一个未设置 `width` 的业务列吸收剩余空间。
- 左树必须具有符合业务语义的根节点并默认展开；组织树等已有稳定语义的结构必须与现有页面保持一致，不得擅自增加“全部”等虚构层级。

### 编辑页和实体引用

- 标准字段、引用选择器和普通命令组成的表单必须使用 `EditPage`。
- `EditPage` 的明细区域或其他使用 `EditSectionCollapse` 的数据卡片需要提供新增、删除、排序等操作时，必须通过 `detailExtra` 或对应分区的 `extra` 将操作统一放置在标题栏右侧。表格通过选择列确定操作目标，禁止新增“操作”列，也不得将操作按钮散落在折叠面板内容区。只有存在明确的特殊交互要求时才允许偏离，并应说明原因。
- 基本身份字段放在“基本信息”；协议、连接、运行参数等领域配置放在独立面板，不把所有字段堆进一个分组。
- 启停、封存等状态不在编辑页展示，也不进入保存或提交类型；新增状态由后端给出安全初值。
- 通用说明性字段统一为 `description`，标签为“描述”。
- 对用户、组织、应用、Feature、账号等实体的选择优先使用 `RefSelector`，保存提交 ID，详情直接返回引用对象用于回显。
- 新增保存后重新查询详情，并将临时页签替换为真实 ID 页签；保存后停留在当前页面。

### 弹框、表格和视觉

- 业务弹框默认使用 `AppModal`；直接使用 Ant Design Modal 仅限简单提示、确认和结果反馈。
- 业务弹框中的标准控件以通用编辑页为视觉基准，默认使用下边框控件和稳定列宽；特殊宽度必须由真实布局需要驱动。
- 页面内容区与工作台边界、同级卡片或块状容器保持 `10px` 间隔；使用通用壳层时不得重复叠加页面级 padding。
- 页面头部没有操作、筛选或状态内容时不渲染空占位。
- CUSTOM 页面中的数据表默认关闭表格内置底部分页，将分页放在所属卡片或区块右上角元信息区。
- 固定高度表格建立从容器到 `.ant-table-body` 的完整 flex 高度链，使横向滚动条固定在内容区底部；禁止用固定 `scroll.y` 撑出伪布局。
- TSX 中禁止 CSS 和内联 `style`；自定义类名以 `sm-` 开头。

## 5. 功能、权限、菜单和页面闭环

新增功能必须能从稳定身份追踪完整闭环：

```text
Feature(featureKey)
├── Permission(permission code)
├── Menu(componentKey + entry permission)
└── PageRegistration(componentKey + featureKey + pageType)
```

- Feature、内置权限和菜单通过新增 Flyway 迁移维护。
- Controller 使用模块权限常量；前端 `permissions.ts` 与后端权限语义一致。
- 菜单入口权限与目标页面必须属于同一 Feature。
- 禁止通过权限码前缀、菜单名称、目录或组件路径推断功能归属。
- 页面注册变更后必须重新生成注册表并确认无差异。

## 6. 完成前复核

提交结果前逐项确认：

- 实现范围与领域文档一致，没有顺手扩展或预建无真实使用方的抽象。
- 后端依赖、事务、日志、权限、引用对象和异常语义符合架构。
- 前端页面类型、页签生命周期、状态职责、选择方式、字段语义和视觉样板一致。
- Feature、权限、菜单、迁移和页面注册形成显式闭环。
- 自动化测试覆盖本模块真实风险，而非机械追求数量。
- 已运行 `scripts/verify-module-conventions.ps1` 以及[质量验证](./verification.md)中与改动风险匹配的命令。
- 最终回复列出验证证据、未验证项和任何仍需用户决策的边界。
