# 集群单例常驻任务

## 定位与边界

`sys/scheduler/singleton` 是任务调度应用中的公共运行能力和管理员控制台。用于一个集群中只需要一个执行者的持续循环、连接监听等任务；按时间触发并结束的任务继续使用 Quartz，短期共享资源互斥继续使用 `DistributedMutex`。各任务独立竞争执行权，不设置承担所有任务的全局主节点，不提供负载均衡、分片执行、工作流或消息补收。

运行定义来自 Spring 显式注册的 `SingletonTask` Bean。代码注册不创建 Feature、菜单或权限；这些目录仍由平台 V4 迁移维护。没有注册任务的发行显示空列表，不启动示例业务。循环和监听的可运行样板位于测试产物 `SingletonProbeProcess`，不随正式 JAR 装配。

本模块为公共能力与监控控制台，不是业务单据。前端采用 LIST 与只读 EDIT，参考现有调度列表与执行详情；没有新增、编辑执行类、删除任务或强制抢占入口。两个下游项目仅作为真实需求依据，本次未迁移它们的代码或数据。

## 所有权和故障语义

- 每个任务使用独立 PostgreSQL session advisory lock，命名空间为 `smart-manage:singleton:{number}` 的 SHA-256 前八字节。候选实例每约2秒竞争一次；数据库会话终止后其他实例可接管。
- 协调连接为独立物理连接，使用应用数据库配置，不能经过事务级连接池代理；不借用业务连接池维持长期锁。物理关闭结束数据库会话，避免解锁失败后把持锁连接归还连接池。
- 每次取得执行权生成新的 UUID `runId` 并递增 `generation`。运行元数据只由实际持锁连接修改，不通过重新连接延续旧执行权；控制命令的 `version` 独立于高频心跳。
- 任务获得锁后为 STARTING，显式调用 `ready()` 后为 RUNNING。管理员停止只更新共享期望状态；执行者观察后进入 STOPPING，取消工作并等待 `run` 和取消回调结束，随后释放执行权。
- 正常下线保留运行期望，资源收束后由其他实例重新运行。停止命令把期望改为停止，因此其他实例不会重新启动。停止中不得重新启动。
- 失去数据库连接或运行代际不匹配时取消旧运行，关闭注册的资源并中断工作线程。本地上下文使用10秒单调时钟有效期，暂停后的旧线程必须在每批新工作及回调前调用 `checkActive()`。
- 数据库读到持有者心跳超过15秒未更新时返回 UNKNOWN，不伪装为 STOPPED，也不据此强制抢锁。数据库检测故障所需时间、竞争间隔及业务初始化共同决定恢复耗时，不承诺瞬时切换。
- 非取消状态下 `run` 正常返回或抛异常都进入失败退避；退避时间由定义指定，保存在共享数据库，其他节点不能绕过。期望为停止时不再安排重试。
- 停止等待预算为12秒；超时记录告警，进程仍存活时不主动释放正常持锁会话、不宣称任务已停止。部署设施最终结束 JVM 后数据库会话释放。任务必须实现有界、可取消的资源生命周期。

每实例最多注册32个任务。每个活跃任务占一个物理数据库连接、一个协调线程和一个工作线程；备用实例短暂建立竞争连接。连接预算须加到现有业务、Quartz 和运维预算中。协调连接固定连接建立超时3秒、SQL超时3秒、socket超时5秒并启用 TCP keepalive；协调连接的这些参数覆盖业务数据库 URL 中的同名值，不改变业务连接池配置。

**所有权不保证业务效果恰好一次。** 网络分区或进程暂停可能造成旧外部请求仍在执行、新持有者已经恢复。平台无法撤回已发送请求，也不能强制终止任意 Java 代码。业务必须实现幂等、结果未知后的核实及必要的目标端隔离。第三方不支持隔离令牌时，不宣称外部连接绝无瞬间重叠。断点、业务进度及断线消息补收归业务模块，不由框架推断。

## 开发者接入

跨领域只依赖 `sm.domain.sys.scheduler.singleton.contract`，不依赖管理 Service、Entity 或 JDBC 协调实现。以下定义值仅为接入示例；使用所属领域的稳定任务编码和已存在的应用编码。

```java
@Component
public class InventoryRefreshTask implements SingletonTask {
    @Override
    public SingletonTaskDefinition definition() {
        return new SingletonTaskDefinition(
                "inventory:refresh", "库存刷新", "inventory",
                "周期读取来源并更新本地库存", true, false, 60);
    }

    @Override
    public void run(SingletonTaskContext context) throws Exception {
        // 初始化所需资源，必要时登记用于唤醒阻塞调用的取消动作。
        context.ready();
        while (!context.cancelled()) {
            context.checkActive();
            // 执行有界的一批业务工作；外部请求必须有超时和幂等语义。
            Thread.sleep(1000);
        }
    }
}
```

定义中的 `controllable` 决定管理端是否允许启停，`autoStart` 只初始化首次运行期望，不能覆盖后续管理员操作；`retrySeconds` 为1～86400秒。任务编码全局唯一且不可复用为不同业务语义。首次装配注册运行行；名称、应用编码、说明和可控性必须与持久定义一致，后续修改通过所属迁移明确交付并安排一致版本部署，不允许混合元数据版本反复覆盖。

`validateControl(boolean)` 适合只读业务前置校验，不能产生外部副作用；真实执行时仍须重新校验凭据、配置和业务条件。需要专用业务命令才能启动的能力应声明 `controllable=false`，不把通用控制台当成绕过业务规则的入口。本版未提供跨领域的共享期望写入 Contract；此类接入需在明确业务命令用例后补充受控接口，不能自行写平台表。

常驻连接应使用 `try/finally` 或 `try-with-resources` 关闭资源，并通过 `context.onCancel(resource::close)` 唤醒阻塞等待。取消回调必须快速、幂等、不等待自己的工作线程；回调和主任务都完成后才释放正常执行权。异步回调捕获本次 `context`，先 `checkActive()` 再派发工作，不能使用最新全局上下文替代旧回调的身份。子线程必须收束后 `run` 才能返回，禁止留下脱离生命周期的后台线程。

数据库业务写入在所属 `TxService` 的真实事务内调用 `context.guardTransaction()`，然后执行本事务的业务写入。该方法要求当前事务绑定平台同一数据源，并在该事务锁住运行行并校验运行身份、代际、期望状态及心跳，接管必须等待事务提交；不在事务外先检查再写入。事务必须短且有界，不能包含外部调用，否则会阻塞心跳及接管。它不保护另一数据库或外部 API。传递到外部系统的 `generation` 只有在目标系统持久拒绝旧代际时才具有隔离效果。

后台执行不继承发起人的登录会话或组织上下文；需要业务范围的任务按所属模块规则显式确定，不能借用管理员登录态。

每次运行以 `runId` 作为 Trace ID，框架在工作线程退出时清理。业务额外线程使用现有 Trace ID 传播机制；异常正文不写入共享状态，框架仅保存安全分类，业务不得在凭据、连接帧和异常中泄露秘密。

## 控制台与权限

- 页面：`sys/scheduler/singleton`、`sys/scheduler/singleton/detail`；Feature 为 `sys/scheduler/singleton`。
- `listPage` 使用 `sys:scheduler:singleton:listPage`；`detail`、`events` 使用 `sys:scheduler:singleton:detail`；`control` 使用 `sys:scheduler:singleton:control`。
- 全部公开 Service 使用 `@AdministratorOnly`，接口同时校验权限码。浏览器继续使用共享会话、Origin 与 CSRF，页面按钮不能代替服务端校验。
- 启停参数只有任务编码、当前 `version` 和运行期望。事务同时保存期望与事件；旧版本拒绝。通用入口不能修改执行类、运行身份、持有者或业务参数。
- 任意装配该任务的应用实例均可接收控制命令；集群查询读取共享运行状态，不把接收请求的备用实例状态当成整个任务状态。未装配的节点显示不可控制，历史任务记录仍可查看。
- 活跃列表和详情每5秒刷新，后台页签暂停轮询。启动成功提示“运行期望已更新”，最终以业务就绪状态为准；停止同理。
- 每任务保留最近200条运行事件，作为有界的排障窗口；管理员命令另由既有操作日志审计。近期事件不构成永久审计或业务执行回执。

## 数据与发布

平台 V4 新增 `t_sys_singleton_task` 与 `t_sys_singleton_event` 以及功能、权限、菜单、数据对象关联。迁移不修改 Quartz 表、不导入两个下游的定义。当前尚无正式发行支持矩阵，执行 V1～V4 空库验证和重复迁移校验；已存在 V3 的环境按新增迁移升级，不修改 V1～V3。

从下游旧实现迁移必须停止旧执行器并确认资源收束，再启用新注册；新旧锁命名空间不同，不能滚动并行启用。正式生产接管验证仍须覆盖部署设施的停机超时、数据库故障检测和目标外部系统。

## 验证入口

按[质量验证](../../development/verification.md)执行普通测试、架构检查、前端检查与真实 PostgreSQL 验证。`SingletonFailoverPostgresTests` 随 `scripts/verify-baseline.ps1` 在随机临时库执行，启动两个独立 JVM，使用真实运行框架和迁移结构：

- 循环任务只由一个进程写入；强杀执行者后备用进程取得新代际；新代际开始后没有旧代际写入。
- 常驻 socket 监听正常下线时先关闭资源，另一个进程恢复执行。
- 从第三个数据库客户端提交停止期望后，执行进程收束，后续不再产生写入；旧命令版本不能重新启动。
- 失败退避在两个进程间共享，备用进程不能立即绕过。

测试只允许 `smart_manage_verify_` 临时数据库，凭据通过子进程环境传入，不写入代码、文档或命令行。输出 `SINGLETON_FAILOVER` 给出本机观察到的接管耗时，不作为生产 SLA。本测试不覆盖 Nginx、真实斗鱼协议、生产网络分区或物理数据库主备切换。
