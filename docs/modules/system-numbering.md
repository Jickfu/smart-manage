# 编号规则

## 模块定位

编号规则是系统建模提供的公共能力，用于业务单据和需要流水编码的主数据。系统稳定身份，例如
`featureKey`、权限码和基础资料分类编码，不使用编号生成器。

后端公共入口为 `NumberGeneratorAccessor`。业务模块必须在自身写事务中调用取号能力，编号流水与业务聚合
共同提交或回滚；系统不提供前端预取号、号码预占或无业务边界的通用 HTTP 取号接口。

## 编号引用

编号引用表达“哪个业务功能的哪个字段需要编号”，稳定键例如：

- `scm/procurement/purchase-requisition.number`；
- `sys/base/basic-data-item.number`。

编号引用通过 `feature_id` 明确归属于 Feature，所属应用和云由 Feature 推导。系统内置引用由 Flyway 建立，
业务模块同时实现 `NumberReferenceProvider`，显式声明稳定引用键、Feature、允许的流水作用域和受控变量。
数据库目录与代码注册不一致时直接失败，不通过规则键、权限前缀、表名或组件路径推断。

一个编号引用可以维护多条规则，但只有一条默认规则。业务可以使用默认规则，也可以像基础资料分类一样，
在同一编号引用内显式选择具体规则。“设为默认”只接受已启用且属于当前引用的规则。

## 格式段

编号格式由有序格式段组成，不执行脚本、SpEL、SQL、表名、数据库字段名或任意对象属性访问。

| 类型 | 配置 | 当前约束 |
| --- | --- | --- |
| `FIXED` | 固定文本 | 不能为空 |
| `VARIABLE` | 代码注册的业务变量 | 当前支持 `org.number`、`category.number` |
| `DATE` | 业务日期变量与格式 | 格式只支持 `yyyy`、`yyyyMM`、`yyyyMMdd` |
| `SEQUENCE` | 流水位数 | 每条规则必须且只能有一个，位数为 1～18 |

每段可以配置段后分隔符，默认由页面建议为 `-`。随机码和任意数据库字段不在当前能力范围。

业务变量由 `NumberVariableResolver` 解析：业务上下文只携带稳定 ID 和业务日期，解析器从所属业务模块读取编码。
组织编码使用 `orgId` 对应组织的 `number`，分类编码使用 `categoryId` 对应分类的 `number`。格式是否显示编码与
流水是否按该对象独立分段相互独立。

## 流水规则

- 流水作用域支持 `GLOBAL`、`ORG` 和 `CATEGORY`，并且必须在编号引用允许范围内；
- 作用域使用稳定 ID 作为计数键，显示编码变化不会重置或合并流水；
- 重置周期支持 `NEVER`、`YEAR`、`MONTH` 和 `DAY`；
- 日期来自业务上下文，不使用浏览器时间；
- 起始值只影响尚未创建的新分段，不重置已有计数器；
- 生成结果最长 64 个字符。

计数器按 `(rule_key, scope_key, period_key)` 唯一分段，使用 PostgreSQL
`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子推进。实现支持多实例，不依赖 Redis 锁或 JVM 锁。

系统保证同一分段内编号唯一、递增，但允许断号：已保存后删除的编号不回收，规则调整也不重编历史数据。
业务表唯一约束仍是最终防线。

## 启停

规则启用和停用使用独立命令及权限，不通过普通保存接口修改状态。仍作为编号引用默认规则，或被
`AUTO_DEFAULT`、`AUTO_LOCKED` 基础资料分类引用的规则禁止停用。管理员必须先切换默认规则或分类规则，
再停用旧规则。

业务取号发现规则停用时直接失败，所在业务事务整体回滚，不生成空编号，也不静默回退到其他规则。
未被自动编号业务引用的停用规则保留历史格式段和计数器。

## 内置配置

| 编号引用 | 默认规则键 | 默认格式 | 作用域 | 重置周期 |
| --- | --- | --- | --- | --- |
| `scm/procurement/purchase-requisition.number` | `scm/procurement/purchase-requisition` | `PR-{bill.bizDate:yyyyMMdd}-{seq:5}` | 组织 | 每天 |
| `sys/base/basic-data-item.number` | `sys/base/basic-data-item` | `BD-{seq:4}` | 基础资料分类 | 不重置 |

采购申请可以在格式中加入 `org.number`；基础资料可以加入 `category.number`。流水仍分别使用稳定的组织 ID 和
分类 ID 分段。

## 接入新单据

新增业务编号需要：

1. 通过 Flyway 建立编号引用和默认规则，并关联真实 Feature；
2. 在业务模块实现 `NumberReferenceProvider`，注册允许作用域和受控变量；
3. 如需新变量，实现独立 `NumberVariableResolver`，不得向用户暴露表名或字段名；
4. 在新增聚合的写事务中，以稳定 `referenceKey` 和业务上下文调用 `NumberGeneratorAccessor`；
5. 保留业务表唯一约束，并覆盖事务、并发、作用域和变量缺失测试。

普通 `BaseBillEntity` 单据只需提供 `orgId` 和 `bizDate`，不需要自行查询组织编码。

## 预览与验证

规则页面使用示例组织编码、分类编码、当天日期和指定流水值渲染格式段。预览不读取或推进正式计数器，
预览结果不能直接作为业务编号保存。

关键验证包括：

- 格式段类型、顺序、变量白名单、日期格式、流水位数和最大长度；
- 正式取号必须存在业务事务；
- 同分段并发取号不重复，不同作用域和周期相互隔离；
- 业务回滚时计数器同时回滚；
- 活跃引用规则不能停用；
- 客户端不能覆盖自动锁定的编号；
- PostgreSQL 唯一约束保留为最终防线。
