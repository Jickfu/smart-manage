# 工作流产品设计草案

更新日期：2026-09-28。状态：方案已确认，当前分支正在实施与验收。

本文补充[工作流领域开发设计方案](./workflow-domain-design.md)，重点定义参与人工作台、管理后台、流程实例控制、任务监控、流转日志和业务单据入口。后端边界、事务和引擎接入仍以[工作流领域](../../smart-manage-server/domains/workflow/docs/process/workflow.md)及既有方案为准。本文位于 `docs/proposals/`，确认前不作为生效规则。

## 1. 产品定位

Smart Manage 的工作流领域是企业管理平台的可选审批与流程运行能力。流程参与入口与流程管理后台必须分开：

| 用户 | 入口 | 主要目标 |
| --- | --- | --- |
| 普通参与人 | 全局消息中心、业务单据 | 查看待办、已办、本人发起；处理自己的任务；查看有权读取的单据审批历史 |
| 流程管理员 | 工作流应用 | 配置、设计、发布和停用流程定义 |
| 流程运维人员 | 工作流应用 | 监控实例和任务、诊断流转、处理运行异常 |

工作流应用不向普通参与人开放。普通参与人即使参与过某个流程，也不会因此获得全局流程实例、任务监控或流转日志的访问权。

工作流管理权限不自动授予业务数据读取权。流程元数据、业务单据、提交快照、审批意见、运行变量和技术诊断信息分别鉴权。

## 2. 设计原则

### 2.1 依托 Warm-Flow，不复制外部产品

Smart Manage 不照搬金蝶的菜单和概念，也不把 Warm-Flow 仅作为流程设计器。定义、实例、任务、历史和运行控制优先使用 Warm-Flow 已有能力，继续通过 `definition / instance / runtime / task / assignment / engine` 边界接入。

“释放 Warm-Flow 能力”不等于把引擎 API 原样暴露给浏览器。所有运行命令必须经过 Smart Manage 的权限、业务状态、事务锁、幂等、审计和消息适配。Warm-Flow 类型、表结构及 `ignore` 等引擎参数只能留在适配层。管理权限允许查看全局流程运行元数据；业务正文与历史快照仍由业务权限、DataScope 或流程参与资格单独保护。

### 2.2 参与人与运维人员使用不同视角

- 消息中心是个人工作台，回答“我现在要处理什么、处理过什么、发起过什么”。
- 流程实例回答“某一轮流程现在处于什么状态、经过哪些节点、可执行哪些实例级干预”。
- 任务监控回答“系统当前有哪些活动或历史任务、由谁处理、哪些任务存在参与人异常”。
- 流转日志回答“引擎和管理命令实际发生了什么”。

不同视角可以复用查询能力，但不能合并为含义模糊的“任务中心”。

### 2.3 管理员可以控制，但不能无痕篡改

流程运维必须能够挂起、恢复、终止、调整当前任务参与人，并在受控条件下退回或跳转。所有干预都要保留原轨迹，记录操作人、原因、前后状态、影响对象和命令结果。管理员不能伪装成审批人，不能生成虚假的同意或拒绝意见。

## 3. 参考产品结论

### 3.1 金蝶 AI 流程平台

2026-09-28 只读观察了用户指定的 Chrome 页签：

- “流程设计”负责模型创建、修改、导入和发布。
- “流程实例”提供挂起、查看单据、查看流程图、强制终止、查看当前任务、查看配置和查看日志等实例级操作。
- “任务监控”展示全局任务、节点和参与人，并允许重新设置参与人。
- “流转日志”展示任务创建、节点完成和引擎消息，面向运维诊断。

Smart Manage 借鉴定义、实例、任务和日志的对象边界，以及从实例进入当前任务的定位方式，不复制流程模板、动态方案和大规模中心分组。

### 3.2 Warm-Flow 和开源产品

- Warm-Flow 1.8.9 已提供实例挂起/激活、终止、撤销、任意通过/退回、转办、委派、加减签、候选人更新和历史查询等能力。
- Warm-Flow 的实例删除会同步删除任务、参与人和历史，不能作为日常运维功能。
- Warm-Flow 的任意跳转和管理员忽略校验能力很强，必须由服务端计算可选目标并锁定实例，不能让前端提交任意引擎参数。
- Camunda 将参与人的 Tasklist 与管理员的 Operate 分开；RuoYi-Vue-Pro 也区分个人待办/已办和管理员流程任务。这与 Smart Manage 的入口边界一致。

## 4. 当前实施基线

1. 工作流应用已移除普通“任务中心”菜单，管理入口为流程定义、流程实例、任务监控和流转日志；个人待办、已办和我发起继续从消息中心进入。
2. 流程实例详情已组合当前任务、候选人、变量、审批历史和管理操作，并提供挂起、恢复、终止、节点调整、变量维护与脚本重试。
3. 候选人维护已进入实例当前任务上下文，不再要求手工输入实例 ID；任务监控可直接打开对应实例。
4. 引擎契约已包装转办、委派、加签、减签和拿回，并将 Warm-Flow 的转办/委派人员类型纳入真实待办资格。
5. 请假业务单据已提供“查看工作流”和“审批意见”，业务鉴权后可切换同一单据的全部历史轮次。
6. 脚本节点已按 Warm-Flow 中间节点扩展实现，支持变量与下一人工节点参与人输出、失败挂起、执行记录和管理员重试。
8. 当前 `WorkflowBusiness.completed()` 由工作流事务主动调用业务回写；虽然状态映射位于业务领域，契约名称和编排方式仍容易让工作流承担业务单据状态所有权。

## 5. 工作流应用信息架构

工作流应用提供四个根级菜单，不再提供“任务中心”菜单，也暂不建立空的“设计中心 / 监控中心”分组：

| 菜单 | 面向用户 | 主要职责 |
| --- | --- | --- |
| 流程定义 | 流程管理员 | 定义、版本、设计、校验、发布、停用 |
| 流程实例 | 流程运维人员 | 查询实例、查看详情、控制实例运行、进入当前任务与日志 |
| 任务监控 | 流程运维人员 | 查询活动/历史任务、定位参与人异常、受审计改派 |
| 流转日志 | 流程运维人员 | 跨实例查询流转事件和管理操作，诊断运行问题 |

现有个人任务页面继续作为消息中心的领域扩展存在，但不生成菜单。页面可保留内部 Feature 注册，任务读取和办理资格仍由候选事实及业务规则决定，不能因为它没有菜单就放宽接口鉴权。

## 6. 流程实例

### 6.1 列表

流程实例使用左树右表。左树为“全部审批业务 → 领域 → 应用”，右表按目录、状态、申请人和时间查询实例。

列表展示单据编号、审批业务、定义及版本、申请人、所属组织、实例状态、当前节点、发起时间、结束时间或最后流转时间。单据编号使用 Link 打开实例详情，列表不设置行操作列；批量或单实例命令统一放在顶部操作区。

实例监控元数据面向获得对应管理权限的流程管理员和运维人员，`org_id` 表示提交时单据所属组织。拥有实例菜单权限不代表可以打开业务单据、附件或提交快照；业务内容继续执行所属领域的权限与 DataScope。

### 6.2 详情工作台

实例详情使用独立页签，不使用弹框。顶部操作区按状态和权限显示：

- 查看业务单据、流程图和流程配置；
- 挂起、恢复；
- 终止流程；
- 管理员退回、管理员跳转；
- 刷新。

详情主体包含：

| 页签 | 内容 |
| --- | --- |
| 实例概况 | 实例、业务、定义版本、申请人、组织、状态和时间 |
| 当前任务 | 活动任务、节点、参与人、创建和到期时间；可进入受审计候选人维护 |
| 审批记录 | 审批人作出的同意、拒绝等业务决定和意见 |
| 流转轨迹 | 节点到达、任务创建/完成、实例状态变化等可解释事件 |
| 操作记录 | 挂起、恢复、终止、跳转、退回、改派等管理员命令 |
| 运行变量 | 脱敏查看和受审计修改，用于分析、修复条件与运行上下文 |

“当前任务”与“任务监控”使用同一任务投影和维护命令。实例详情负责单实例上下文，任务监控负责跨实例检索。

## 7. 任务监控

任务监控至少提供“活动任务”和“历史任务”两个视图，可按审批业务、实例状态、任务状态、节点、参与人和时间筛选。

活动任务展示实例、单据、节点、当前候选人、任务创建时间、持续时长和异常标记。第一阶段异常标记至少覆盖：

- 没有有效候选人；
- 候选人全部停用；
- 实例已挂起；
- 超过配置时限但仍未处理。

“维护候选人”移动到任务监控的顶部操作区，并可从实例详情的“当前任务”页签调用。操作自动带入实例、任务、节点和当前候选人，只允许更换候选集合，必须填写原因；不能代审批、推进节点或伪造审批记录。

工作移交、批量改派和催办可在形成明确规则后扩展。转办、委派和加减签属于当前处理人的任务协作能力，应通过消息中心的任务处理区按流程策略开放；管理员异常改派与参与人的转办/委派必须使用不同命令、权限和日志动作。

## 8. 流转日志与审计

系统区分三类记录：

| 记录 | 含义 | 主要读者 |
| --- | --- | --- |
| 审批记录 | 审批人作出的业务决定和意见 | 业务用户、参与人、管理员 |
| 流转日志 | 实例、节点和任务的生命周期事件 | 流程运维人员 |
| 操作记录 | 管理员运行干预及其前后状态 | 流程运维和审计人员 |

独立“流转日志”页面支持跨实例查询；实例详情中的“流转轨迹”和“操作记录”是同一数据在当前实例范围内的投影。

流转日志应转换为稳定、可理解的 Smart Manage 事件，不默认返回 Warm-Flow 原始 JSON、内部表字段或未脱敏变量。Warm-Flow 历史无法完整表达的管理员干预，写入独立且不可修改的操作记录；不复制第二套实例和任务状态。

## 9. 运行控制能力

### 9.1 挂起与恢复

- 挂起阻止实例继续办理，不改变业务单据的“审批中”状态。
- 恢复后继续使用原活动任务和候选人。
- 挂起和恢复均要求独立权限、原因和操作记录。
- 已结束实例不能挂起或恢复。

### 9.2 管理员终止

- 终止结束当前活动任务和实例，保留全部历史，不等同于审批拒绝或申请人撤回。
- 工作流结果增加独立 `TERMINATED`，不得伪装为 `REJECTED` 或 `WITHDRAWN`。
- 工作流只记录自身终止状态并发布结果通知，不决定业务单据状态。
- 终止前展示受影响任务和将发布的结果通知，必须填写原因并二次确认。

### 9.3 管理员退回与跳转

产品上拆成两个动作，避免一个“任意跳转”同时表达不同意图：

- 管理员退回：目标只能是服务端计算出的已执行人工节点，用于纠正错误流转。
- 管理员跳转：可前进或后退到服务端计算出的可达人工节点，用于异常修复，使用更高权限。

执行前必须预览将结束的活动任务、目标节点、将创建的任务和候选人。执行后保留原任务历史，以 `ADMIN_RETURN` 或 `ADMIN_JUMP` 记录结束原因，不能覆盖原审批意见。浏览器不能提交 Warm-Flow 的 `ignore` 参数或任意节点编码。

### 9.4 运行变量

流程运维人员可以修改流程变量。该能力使用独立命令和权限，不直接编辑 Warm-Flow 表或提交整份原始 JSON：

- 实例必须先挂起，修改完成后由管理员显式恢复，避免变量修改与任务推进竞争；
- 支持新增、修改和删除普通流程变量，并校验变量名、JSON 类型、大小和定义声明；
- 业务标识、实例/定义标识、引擎保留字段和 Smart Manage 系统字段不可修改；
- 展示修改前后值、引用该变量的后续条件或人员规则，并要求填写原因；
- 变量修改只影响后续条件计算和任务创建，不改写历史任务快照，也不会自动重算已经激活并冻结的候选人；当前任务仍通过候选人维护处理；
- 每次修改写入不可变操作记录，敏感值按字段策略脱敏。

### 9.5 删除实例

流程实例不可删除。系统不提供页面按钮、业务 API、批量命令或后台维护入口。Warm-Flow 的删除会同时移除任务、参与人和历史，破坏审计链，因此引擎适配层也不能向上层暴露实例删除能力。

错误或不再需要的运行实例只能“终止”，并保留实例、任务、审批、流转和管理操作的完整历史。测试环境需要清理数据时，通过环境整体重建或数据库基线重置完成，不对单个流程实例执行删除。

### 9.6 统一执行约束

所有运行命令必须：

1. 校验独立权限和业务可干预规则；
2. 锁定业务单据和实例，复用既有事务与命令幂等机制；
3. 再次校验实例、任务和目标节点的实时状态；
4. 原子执行引擎命令、结果通知、操作记录和消息 Outbox；
5. 失败时整体回滚，不留下业务状态与引擎状态不一致的半成品。

## 10. 普通参与人的入口

全局消息中心继续提供“待处理、已处理、我发起的”，并进入现有审批工作台：

- 待办默认打开“任务处理”；已办和我发起默认打开“审批记录”。
- 左侧展示本轮业务快照，右侧展示任务处理和审批记录。
- 当前处理人可使用哪些转办、委派、加签、减签或拿回能力，由流程定义策略和任务实时状态共同决定。
- 普通参与人不进入流程实例、任务监控或流转日志列表。

## 11. 业务单据上的工作流能力

接入审批的业务单据在顶部操作区提供：

### 11.1 查看流程

- 有活动轮次时默认打开当前轮次，没有活动轮次时打开最近一轮。
- 打开受业务权限约束的实例详情投影；业务用户不因这个入口获得管理员命令。
- 多轮次按“第 N 轮、状态、发起时间、定义版本”切换，展示该轮实际使用的流程图和记录。

### 11.2 审批意见

- 使用轻量只读弹框，按轮次倒序分组。
- 展示节点、处理人、动作、意见和时间。
- 管理员干预明确标识为系统操作，不冒充审批意见；可跳转到有权访问的实例详情。
- 历史轮次读取提交时快照和附件引用，不能用当前主单内容冒充历史。

工作流按 `businessType + businessId` 查询全部轮次；业务表只保存当前/最近实例摘要，不复制实例列表。

## 12. 工作流结果与业务单据状态

工作流状态和业务单据状态分别拥有：

- 工作流领域只维护实例及任务状态，并产生 `APPROVED`、`REJECTED`、`WITHDRAWN`、`TERMINATED` 等稳定结果；
- 工作流完成或终止后发布包含 `businessType`、`businessId`、`instanceId`、结果和发生时间的结果通知；
- 业务领域注册结果处理器，自行决定是否转换 `bill_status`、记录最近结果或触发其他业务命令；
- 工作流代码不得包含“通过变 C、拒绝变 A”等业务映射，也不得直接访问业务 Entity、Mapper 或表；
- 同一进程内需要强一致的业务处理器可以作为事务参与者同步响应结果；用户消息和其他可重试副作用继续通过 Outbox 投递；
- 业务处理器失败必须阻止流程命令提交，不能出现实例已结束而业务事务被静默跳过的状态。

现有 `WorkflowBusiness.completed()` 应调整为表达“业务领域响应流程结果”的稳定契约，名称和模型不能暗示工作流拥有业务状态。请假样板如何映射结果继续由请假聚合决定，不再作为流程终止命令的产品规则。

## 13. 脚本节点

### 13.1 Warm-Flow 支持边界

Warm-Flow 1.8.9 没有独立的脚本节点枚举，内置类型只有开始、中间、结束、互斥网关、并行网关和包容网关。它提供节点扩展属性、LogicFlow 自定义节点、开始/分派/完成/创建监听器、流程变量和动态参与人能力。

Smart Manage 可以提供产品级“脚本”节点，但在 engine 适配层将其映射为带有固定扩展标记的 Warm-Flow 中间节点，不修改或 fork Warm-Flow 的 `NodeType`。读取定义时根据扩展标记还原脚本节点；保存时转换回 `nodeType=1` 和 Smart Manage 扩展数据。设计器通过官方 `customNodes`、`paletteNodes`、属性插槽及保存钩子集成脚本节点，不能把无法往返的自定义 LogicFlow 类型直接写入 Warm-Flow。

### 13.2 节点语义

脚本节点是系统自动任务，不产生个人待办。节点到达后执行固定版本脚本：

1. 输入当前流程变量、业务引用、实例、定义版本和节点上下文；
2. 返回流程变量增量，以及后续节点需要的参与人结果；
3. 服务端校验输出的变量类型、目标节点和候选用户；
4. 合并变量并由系统身份自动完成脚本任务，Warm-Flow 再使用新变量计算网关和创建后续任务；
5. 记录执行脚本快照摘要、输入摘要、输出、耗时和结果。

动态参与人通过结构化返回值 `participants` 指定紧随脚本节点创建的人工任务候选人；脚本不能直接操作 Warm-Flow Task、User、Mapper 或数据库。需要跨过网关指定更远节点人员时，先输出流程变量，再由后续人员规则解析，不能让脚本直接修改任意活动任务。

脚本失败时不自动越过节点。系统保留该自动任务，挂起实例并在任务监控中标记“脚本执行失败”；管理员可以查看脱敏错误、修改允许的流程变量后重试，也可以使用管理员跳转或终止。重试使用同一已发布脚本快照并具备命令幂等，不能在运行实例上临时替换脚本源码。

### 13.3 与脚本控制台的关系

现有脚本控制台是 administrator 的应急运维工具，允许通过 `app.getService()` 调用公开领域 Service，保存脚本可修改或删除，并使用全局执行锁；这些语义不适用于自动流程节点。

脚本节点复用其经过验证的 GraalJS 安全原则和底层实现能力：无 HostAccess、类查找、反射、文件、网络、进程、原生能力和线程，按次创建 Context，并限制源码、输出和执行时间。实施时将与业务无关的沙箱执行核心提取为平台通用能力：

- 脚本控制台继续组合 `app` 服务网关、管理员复核、全局互斥和控制台审计；
- workflow 只组合受限 `flow` 上下文、按实例串行和节点执行记录；
- 平台通用沙箱不认识 workflow，排除 workflow 后脚本控制台保持正常；
- workflow 不复用控制台已保存脚本，发布流程时固化节点脚本源码、摘要和配置，保证历史版本可重现。

脚本节点第一版只允许纯计算和结构化输出，不允许调用领域 Service、数据库，或产生网络、消息、文件等外部副作用。该边界已经确认，不提供按脚本或流程定义放宽沙箱的开关。需要调用业务能力时，应另行设计具有幂等、重试和补偿语义的服务任务节点。

## 14. 权限与 Feature

当前形成以下 Feature：

| Feature | 是否生成菜单 | 权限范围 |
| --- | --- | --- |
| `workflow/process/definition` | 是 | 列表、设计、保存、发布、停用 |
| `workflow/process/instance` | 是 | 列表、详情、挂起、恢复、终止、退回、跳转、修改变量、重试自动节点 |
| `workflow/process/task-monitor` | 是 | 列表、详情、维护候选人、批量改派 |
| `workflow/process/flow-log` | 是 | 流转日志和操作记录查询 |
| 个人任务内部 Feature | 否 | 消息中心领域视图和页面注册；办理资格由任务事实决定 |

危险命令使用独立权限码，不能用一个“实例维护”权限覆盖全部命令。管理权限只覆盖流程运行元数据和对应命令，不授予业务正文、附件或历史提交快照权限。

当前分支尚未发布时直接修正目录迁移基线，不保留旧“任务中心”菜单或旧候选人维护权限的兼容入口。

## 15. 实施范围与顺序

本轮将已确认能力作为同一发布范围，不再把跳转、转办、委派和加减签留到未来版本。实施仍按依赖顺序拆分，以便每一步可验证：

- 移除工作流应用的“任务中心”菜单，保留消息中心个人任务扩展；
- 新增流程实例、任务监控和流转日志；
- 实例详情提供当前任务、审批记录、流转轨迹、操作记录和脱敏运行变量；
- 候选人维护移动到任务监控，并从实例当前任务复用；
- 支持挂起、恢复、管理员终止、管理员退回、管理员前后跳转和流程变量修改；
- 支持参与人的转办、委派、加签、减签和拿回，并在流程定义中配置允许的任务操作；
- 支持脚本自动节点、变量输出、动态参与人、失败挂起和受审计重试；
- 业务单据增加“查看流程”和“审批意见”，支持多轮历史；
- 完成真实 PostgreSQL、前后端门禁与浏览器验收，并把最终约束同步到生效领域文档。

同一发布范围不表示同时堆叠开发。先完成实例、任务、日志、权限与操作记录骨架，再接入每种命令和脚本节点；每项通过事务、并发和浏览器验收后继续下一项。

## 16. 本轮已固定的细化规则

1. 转办、委派、加签和减签只能由当前任务真实候选人执行；服务端再次校验任务活动状态和目标人员，操作失败整体回滚。首版不增加流程定义级开关。
2. 加签沿用 Warm-Flow 当前任务加签语义，不区分前加签、后加签或并行加签；减签只能移除引擎当前允许移除的未处理人员。更复杂的加签模式以后作为独立能力设计。
3. 脚本读取 JSON `workflow`，返回 `{ variables, participants }`；普通变量最多 100 项、结果不超过 100KB，参与人最多 100 名启用用户，执行超时 3 秒。变量保留业务/实例标识以及 `sm.`、`warm.` 命名空间。
4. 管理后台权限面向全局流程运行元数据；业务单据正文与历史快照通过业务领域权限、DataScope 或参与资格读取，不在工作流管理权限中隐式放开。

## 17. 验收基线

- 普通参与人只从消息中心和业务单据进入个人任务，不看到工作流应用的管理菜单。
- 流程运维人员可以从实例、任务和日志三个视角定位一条运行流程的现状与完整历史。
- 没有业务读取权时，管理员可以看授权范围内的流程元数据，但不能读取业务正文、附件和未脱敏变量。
- 挂起后任务不能继续办理，恢复后原任务可继续；业务单据状态保持审批中。
- 终止、退回、跳转和候选人维护不会生成伪审批意见，均有独立操作记录。
- 修改流程变量必须先挂起实例，恢复后只影响后续流转；历史变量和已激活候选人保持不变。
- 脚本节点不进入个人待办；成功后自动推进，失败时挂起并可在任务监控中诊断和幂等重试。
- 脚本尝试访问领域 Service、数据库、网络、文件、消息或宿主 Java 能力时必须失败，且不能留下部分变量更新或任务推进。
- 工作流结束只产生工作流结果和结果通知，业务状态转换由业务领域处理器决定。
- 任何角色和业务接口都不能删除流程实例；终止后的实例仍可完整查询。
- 一个业务对象多次提交后，可查看每轮独立的状态、意见、流程图和历史快照。
- 任务监控可以直接选中活动任务维护候选人，不再手工输入实例 ID。
- 任何运行命令失败时，引擎、业务状态、操作记录和消息不会出现部分成功。
- 排除 workflow 后，platform 仍能独立构建、启动和使用；平台代码不新增 workflow 类型或条件分支。
