# 单据状态架构

本文档是业务单据状态编码、扩展、流转及与工作流关系的权威来源。具体业务状态和命令仍由所属领域文档定义。

## 标准状态

具有保存、提交、审核等生命周期的业务单据继承 `BaseBillEntity`，Java 字段统一为 `billStatus`，数据库字段统一为 `bill_status char(1) NOT NULL DEFAULT 'A'`。

选择 `char(1)` 是为了形成直观、稳定、受约束的单字符业务协议，而不是为了宣称它比 `integer` 有性能或空间优势；PostgreSQL 的实际存储和对齐收益不应作为该设计依据。

| 值 | Java 名称 | 中文名称 | 固定语义 |
| --- | --- | --- | --- |
| A | `SAVED` | 暂存 | 已持久化、允许普通修改、尚未提交 |
| B | `SUBMITTED` | 已提交 | 已离开暂存状态，普通保存禁止 |
| C | `AUDITED` | 已审核 | 审核成功完成，不包含审核拒绝 |
| D | `CLOSED` | 已关闭 | 业务生命周期终态，默认不可恢复 |

新增页尚无已持久化单据，不具有单据状态；前端使用 `OperationType.ADDNEW` 表达新增形态并隐藏状态字段。首次保存后为 A；新增直接提交在同一事务中完成聚合保存和 A 到 B 的转换，页面只展示提交后的真实状态。

## 业务扩展

A-D 由平台永久保留，业务不得覆盖或改名。E-Z 由具体业务聚合按需扩展；同一编码可以在不同聚合中表达不同含义，但在所属聚合内必须唯一、稳定，并记录在表字段备注和领域文档中。平台不得在没有迁移方案时把已经开放的 E-Z 重新解释为新的全局状态。

后端使用 `BillStatusPolicy.standardBuilder()` 合并扩展定义、可编辑状态和转换规则。平台策略默认提供：

- 初始状态 A；
- A 允许普通保存；
- 提交 A → B；
- 审核 B → C。

D 的允许来源、恢复能力及任何 E-Z 转换由业务显式配置。公共策略只计算和校验状态，不访问数据库、不处理权限，也不代替领域事务。业务 TxService 必须读取或锁定数据库当前记录，校验权限、状态和并发版本，再以当前状态和版本作为原子更新条件。

## 数据库约束

每张业务单据表显式声明自己的允许集合，例如仅使用标准状态时：

```sql
bill_status char(1) NOT NULL DEFAULT 'A'
    CHECK (bill_status IN ('A', 'B', 'C', 'D'))
```

使用扩展 E 时把 E 加入本表约束，并在字段备注中说明含义。不得使用全局 PostgreSQL ENUM、全局状态字典外键或平台业务表承载可选领域的状态集合。索引只按真实查询需要增加，不能因字段是状态就机械建索引。

## 命令与前端

`billStatus` 不进入普通保存 Form，客户端不得通过保存接口直接指定状态。提交、审核、关闭及业务扩展状态使用独立命令；服务端根据数据库当前状态、权限、业务角色和 version 再次校验。

前端公共单据状态目录提供标准名称、颜色、筛选选项和扩展合并。页面壳层不解释状态码；领域页面根据自身策略显式传入是否可编辑。新增页隐藏状态，已有单据以只读文本展示当前状态。未来需要选择目标状态时，前端只能展示服务端允许的目标集合，最终转换仍由专用命令在服务端校验。

## 工作流边界

单据状态表达业务聚合当前生命周期；工作流状态表达审批实例运行事实。工作流领域只返回 `APPROVED`、`REJECTED`、`WITHDRAWN` 等结果，不拥有、读取或直接修改业务表的 `bill_status`。

业务领域负责结果映射。例如可修改重提的单据可以把 `APPROVED` 映射为 C，把 `REJECTED`、`WITHDRAWN` 映射回 A，并通过审批历史或领域结果字段保留上一轮结果；拒绝后终止的业务也可以映射到自己的 E。工作流不能假设 `APPROVED` 必然等于数据库值 C。
