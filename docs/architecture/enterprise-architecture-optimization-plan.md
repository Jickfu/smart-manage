# Smart Manage 企业级架构优化计划

## 1. 文档定位

本文档是 Smart Manage 唯一持续维护的长期优化路线图和任务状态来源，用于指导项目从当前架构内核演进为可实际使用、可长期维护、符合主流社区习惯的企业级系统。

- `AGENTS.md` 记录已经生效、开发时必须遵守的规范。
- 本文档记录尚未完成的优化事项、实施顺序、边界和验收标准。
- `architecture-closure-report.md` 只作为历史收口报告保留，不再承担未来计划职责。
- 具体阶段完成并形成稳定规则后，再将必要约定同步到 `AGENTS.md`。
- 已完成事项只保留结论和完成日期，不保留已经失效的详细实施步骤。

### 1.1 状态定义

| 状态 | 含义 |
|---|---|
| `待实施` | 已确认需要实施，但尚未开始 |
| `实施中` | 当前正在实施，尚未满足全部验收标准 |
| `已完成` | 已满足验收标准，并完成必要验证 |
| `暂缓` | 当前不实施，达到明确启动条件后重新评估 |
| `不实施` | 已确认不属于本计划范围 |

### 1.2 维护规则

每个阶段必须包含目标、问题依据、修改内容、明确边界、验收标准和前置依赖。阶段实施时应保持最小充分范围，不夹带无关重构。

项目质量不以业务模块数量、测试数量或覆盖率衡量。测试采用风险驱动策略，优先保护架构边界、安全逻辑、状态流转、事务、并发和关键前端生命周期，不为 Getter、Setter、普通 CRUD、简单转换和框架生成代码增加低价值测试。

## 4. 阶段一：恢复工程质量门禁

**状态：** `实施中`

已完成格式门禁、编码/行尾规则、CI 后端测试、前端检查/测试/构建、注册表差异检查和空库迁移任务。GitHub 主分支保护属于仓库外部设置，仍需在仓库设置中启用后才能完成本阶段。

### 4.1 目标

使主分支始终处于可重复编译、测试、格式检查、构建和数据库初始化的状态，避免文档声明与实际工程门禁不一致。

### 4.2 问题依据

- 当前 120 个前端文件未通过 Prettier 检查。
- 本地 Windows 环境与 CI 环境可能产生行尾、编码和工具版本差异。
- 当前缺少覆盖后端、前端、组件注册表和 Flyway 的统一 CI。

### 4.3 修改内容

- 修复现有前端格式问题。
- 增加 `.editorconfig`，统一 UTF-8、末尾换行、缩进和行尾规则。
- 明确 Git 行尾策略，并保证 Windows 与 Linux 检出结果一致。
- 固定 JDK、Node.js、Maven 和 pnpm 的受支持版本。
- 建立 GitHub Actions，按顺序执行：
  1. 后端 `mvn test`。
  2. 前端 `pnpm lint`。
  3. 前端 `pnpm format:check`。
  4. 前端 `pnpm build`。
  5. 重新生成组件注册表，并确认工作区没有差异。
  6. 在空 PostgreSQL 数据库顺序执行全部 Flyway 迁移。
- 主分支保护应要求上述流水线全部通过，不允许以忽略错误的方式继续执行。
- 依赖升级暂时由人工定期审计，不引入 Dependabot、Renovate 或其他自动升级机器人。

### 4.4 明确边界

- 本阶段不修改业务接口、数据库结构或业务页面行为。
- 不评估、不升级 JetCache RC 版本。
- 不用降低 ESLint、Prettier、TypeScript 或构建告警标准的方式通过门禁。
- 自动生成文件必须通过生成命令维护，禁止人工修补生成结果。

### 4.5 验收标准

- 全新检出代码后，一条 CI 流水线可完成全部验证。
- 本地与 CI 的格式检查结果一致。
- 组件注册表生成后无未提交差异。
- 空数据库能够顺序执行全部 Flyway 迁移。
- 任一门禁失败时，主分支合并被阻止。

### 4.6 前置依赖

无。

## 5. 阶段二：选择性引入 MapStruct

**状态：** `已完成`

已于 2026-07-27 完成 MapStruct 统一配置和采购申请、`sm.domain.sys` 现有手写 VO 转换迁移。纯字段映射均位于模块内 Converter；附件访问地址、菜单父级、任务运行状态等仍由 Service 以 `assemble...` 语义显式组装。后续新增模块继续按本节规则实施。

### 5.1 目标

面向后续 ERP、MES 等大型业务系统中持续增长的 Entity、列表 VO、详情 VO、选择 VO 和明细 VO，使用编译期安全的方式降低重复字段映射和漏映射风险，同时保持查询与业务组装显式可读。

### 5.2 问题依据

- 当前已有 65 个 VO、26 个 Entity，转换方法分布在多个 Service 中。
- 现有命名同时存在 `toListVo`、`toListVO`、`toRoleListVO` 等形式。
- 部分 `toDetailVo` 只是纯字段复制，部分方法却包含数据库查询，方法名无法表达真实成本。
- 随业务系统扩展，手工 setter 数量会快速增长，字段变更时容易产生静默漏映射。

### 5.3 架构结论

引入 MapStruct 1.6.3 稳定版，但仅将其作为纯对象映射工具：

- `Entity → ListVO`、`SelectVO`、`EntryVO` 和基础 `DetailVO` 的纯字段转换使用 MapStruct。
- MyBatis XML 联表查询直接投影 VO 的实现保持不变，不为了使用 MapStruct 先查询 Entity 再转换。
- 数据库查询、缓存访问、权限判断、默认值计算、状态规则、树结构聚合和主从组装禁止放入 MapStruct。
- 含查询或业务处理的方法使用 `assemble...` 命名，不再使用容易误导的 `to...VO`。
- 转换组件统一使用 `*Converter` 命名，避免与 MyBatis `*Mapper` 混淆。
- 不使用 `BeanUtils.copyProperties` 等运行时反射方案。
- 不建立全局万能 Converter，不额外增加 DDD 分层。

### 5.4 技术配置

- Maven 增加 `org.mapstruct:mapstruct:1.6.3`。
- `maven-compiler-plugin` 的注解处理器同时配置 MapStruct、Lombok 和 `lombok-mapstruct-binding`。
- 在第三方框架配置边界建立统一 `@MapperConfig`，配置：
  - Spring component model。
  - 构造器注入。
  - 未映射目标字段按编译错误处理。
  - 不允许静默忽略新增目标字段。
- Converter 放在对应单据或模块内部，由 Service 构造器注入。
- 同名、兼容类型字段允许自动映射。
- Long/String、枚举/编码、字段重命名和语义转换必须显式声明。
- Entity 新增字段不得自动进入未声明的外部接口模型。

### 5.5 实施顺序

1. 以采购申请试点，迁移主单列表 VO 和明细 VO 的纯字段映射。
2. 以角色模块试点，保留纯字段 Converter，并将带权限关系查询的详情逻辑改为显式组装。
3. 执行编译和后端测试，验证 Lombok、Spring 注入、MyBatis-Plus、雪花 ID 和 JSON 序列化行为。
4. 根据两个试点形成稳定规则，再按模块逐批迁移。
5. 每次只迁移一个模块，不进行全仓库一次性重写。

### 5.6 明确边界

- 不改变外部 API 路径、请求参数、响应 JSON 或 VO 字段类型。
- 不改变现有 MyBatis 查询策略。
- 不在 `@AfterMapping`、表达式或默认方法中隐藏数据库查询和业务规则。
- 不为简单生成映射编写逐字段单元测试，映射完整性主要由编译期规则保证。
- 复杂业务组装继续由 Service 显式控制。

### 5.7 验收标准

- 新增 VO 目标字段未处理时编译失败。
- Converter 中不存在 Mapper、Service、缓存、安全上下文或外部资源依赖。
- `RoleService.toDetailVo` 一类包含查询的方法改为含义明确的详情组装。
- 采购申请和系统领域现有模块的外部 API 响应结构保持不变。
- 不再出现新增的命名不一致手工 `to*Vo` 方法。
- 后端测试全部通过。

### 5.8 前置依赖

阶段一完成。

## 6. 阶段三：架构规则自动化

**状态：** `已完成`（2026-07-27）

已增加基础层依赖、Controller 依赖、公开 Service 事务、TxService 声明、Converter 纯度、`@BizLog` 使用位置和高风险管理员校验检查；页面注册业务键重复检查由注册表生成脚本和 CI 无差异校验共同承担。

### 6.1 目标

将核心架构约定转化为少量稳定、可自动验证的规则，减少仅依靠文档和人工评审维护边界的风险。

### 6.2 问题依据

- 当前架构约定较多，但自动化架构测试只覆盖少量依赖方向。
- 项目扩展到 ERP、MES 后，跨模块直接依赖和绕过事务入口的风险会显著增加。
- MapStruct 引入后需要防止 Converter 演变为隐藏业务逻辑的组件。

### 6.3 修改内容

增加高价值架构测试或等价静态检查：

- `sm.system` 和系统内核禁止依赖可选业务领域。
- Controller 禁止依赖 Mapper 或 TxService。
- 公开 Service 禁止声明 `@Transactional`。
- `*TxService` 必须包级可见，并声明类级事务。
- `@BizLog` 只能出现在公开 Service 的业务命令方法。
- SQL、脚本、Arthas 等高风险能力必须在公开 Service 校验 `administrator`。
- MapStruct Converter 禁止依赖 Mapper、Service、缓存、安全上下文和外部资源。
- 组件注册表发现重复业务键时必须生成或构建失败。

### 6.4 明确边界

- 不引入机械覆盖率目标。
- 不测试 Getter、Setter、普通 CRUD、简单 Converter 或框架生成代码。
- 不为了自动检查增加复杂的自研规则引擎；优先使用简单、可读的测试。
- 规则必须对应真实架构风险，不因个人代码风格增加门禁。

### 6.5 验收标准

- 违反上述边界的最小反例能够导致测试或构建失败。
- 现有合法 Service、TxService、Mapper 和 Converter 能通过检查。
- 检查失败信息能够指出违反的规则和类。
- 后端测试与前端构建全部通过。

### 6.6 前置依赖

阶段二完成并形成稳定映射边界。

## 7. 阶段四：关键风险测试闭环

**状态：** `实施中`

已增加采购申请事务测试、Long 反序列化失败测试、日志敏感字段脱敏测试，以及前端页签替换、脏数据关闭和页签容量测试；认证、文件补偿、Flyway 集成及完整纵向端到端场景仍待实施。

### 7.1 目标

建立精简、风险驱动的测试体系，保护生产风险和架构核心，不通过大量低价值测试增加项目维护负担。

### 7.2 问题依据

- 后端当前测试数量少，多个安全和基础设施边界缺乏验证。
- 前端尚无自动化测试。
- 采购申请的页签生命周期、主从事务和并发冲突仍较依赖人工验收。

### 7.3 后端优先场景

- 登录、验证码、SM2 解密和认证失败。
- 权限缓存失效和高风险管理员身份校验。
- 全局异常映射和 Long 反序列化失败。
- 乐观锁、状态流转、主从事务和并发冲突。
- 文件存储失败后的数据库与文件补偿。
- Flyway 空库初始化。

### 7.4 前端优先场景

- Query Key 和命令成功后的缓存失效。
- 新增临时页签替换为真实单据页签。
- 保存、提交和只读状态转换。
- 脏数据关闭确认。
- 401、业务异常和网络错误处理。
- 页面权限和组件注册白名单。

### 7.5 端到端验收

只保留一条采购申请核心流程：

1. 登录并进入采购申请列表。
2. 新增采购申请并保存。
3. 临时页签替换为真实 ID 页签并回显详情。
4. 修改并提交单据。
5. 提交后进入只读状态。
6. 并发版本冲突得到明确提示。

### 7.6 明确边界

- 不设置行覆盖率、分支覆盖率或测试数量指标。
- 不为简单映射、普通 CRUD、纯展示组件和第三方框架行为编写测试。
- 不复制大量仅数据不同的 UI 用例。
- 测试必须验证业务不变量或架构风险，无法说明保护目标的测试不纳入。

### 7.7 验收标准

- 每个列出的高风险类别至少有一个能防止真实回归的自动化场景。
- 采购申请核心端到端流程可重复执行。
- 测试失败能够表达业务原因，不依赖脆弱的内部实现细节。
- 测试套件执行时间适合在 CI 中持续运行。

### 7.8 前置依赖

阶段一完成；可与阶段二并行，但涉及 Converter 的规则在阶段二之后补齐。

## 8. 阶段五：保留 localStorage 并进行安全加固

**状态：** `实施中`

已完成 401 本地认证清理、服务端主动注销、CSP 和 Referrer 策略；生产环境浏览器验证、CSP 内联脚本收紧及完整安全测试仍待实施。

### 8.1 目标

保持当前前后端分离和 Sa-Token 传递协议，不迁移 Cookie，通过减少 XSS、凭据残留、日志泄漏和高风险入口暴露来提升生产安全。

### 8.2 问题依据

- token 当前保存在 localStorage，浏览器脚本一旦被注入即可读取。
- 登录页是独立 HTML，需要单独纳入 CSP 和输出安全检查。
- 项目包含 SQL、脚本和 Arthas 等高风险管理能力。
- 演示环境需要保留固定默认管理员凭据，不能使用首次登录强制改密。

### 8.3 修改内容

- 配置严格 CSP，限制脚本、样式、图片、连接和其他资源来源。
- 检查所有不可信 HTML 输出路径，禁止未审查的 HTML 注入。
- 为 token 设置合理有效期，并支持主动注销和服务端失效。
- 401 时清除 localStorage 和 Zustand 中的认证状态，再跳转登录页。
- 操作日志、异常日志和认证日志禁止记录 token、密码、验证码、私钥和密钥。
- SQL、脚本和 Arthas 保留权限码与 `administrator` 身份双重校验。
- Swagger、Scalar、Actuator 和高风险控制台按环境限制开放。

管理员凭据按环境区分：

- 演示环境允许固定默认账号和密码，便于公开体验。
- 生产环境必须通过显式配置提供初始管理员凭据。
- 生产配置缺失时不得静默回退到演示凭据。
- README 明确区分演示环境和生产环境的安全责任。

### 8.4 明确边界

- 不迁移到 Cookie 认证。
- 不改变前端 `smtoken` 请求头协议。
- 不实施管理员首次登录强制改密。
- 不以 SM2 或请求加密代替 TLS。
- 前端权限只控制展示，后端仍是最终鉴权边界。

### 8.5 验收标准

- CSP 不影响正常登录和应用加载，并能阻止非允许来源脚本执行。
- 401 后本地认证状态被完整清除。
- 日志中不出现敏感凭据。
- 非 `administrator` 即使拥有可配置权限码也无法调用高风险能力。
- 生产环境不能意外使用演示管理员凭据。

### 8.6 前置依赖

阶段一完成。

## 9. 阶段六：公共基础设施与前端框架治理

**状态：** `待实施`

### 9.1 目标

防止后端公共层和前端公共页面随着业务增加演变为无边界的万能基础设施，保持后续 ERP、MES 业务扩展的可维护性。

### 9.2 后端修改内容

- 定义公共能力准入条件，防止 `sm.system` 吸收具体领域语义。
- 统一缓存 Key、TTL、空值策略、事务提交后失效和多节点一致性语义。
- 明确数据库事务与 Local、FTP 等外部文件存储不能原子提交时的补偿策略。
- 完善 Trace ID 在异步线程、操作日志和任务执行中的传播。
- 检查 Quartz 任务的幂等、重复执行、失败恢复和集群语义。
- 避免 `SpringContextHelper` 演变为通用服务定位器。

### 9.3 前端修改内容

- 限制 `EditPage` 继续增加具体业务状态和命令参数。
- 公共页面只负责布局、加载、错误、权限、基础表单和通用交互。
- 领域页面或领域 Hook 负责保存、提交、审核等业务生命周期。
- 明确公共组件扩展点，但不建设低代码字段引擎。
- 统一命令错误反馈，避免公共组件静默吞掉非表单异常。
- 为未卸载页签建立容量、关闭和资源释放策略。
- 分析 Ant Design 大块产物和首屏依赖，使用真实构建数据决定拆分策略。

### 9.4 明确边界

- 不增加 Application、Domain、Infrastructure 等额外后端层级。
- 不为采购申请建立专属公共框架。
- 不通过提高构建告警阈值掩盖产物体积问题。
- 不因理论复用提前创建没有第二个使用方的抽象。

### 9.5 验收标准

- `sm.system` 不包含具体业务领域依赖或语义。
- 缓存和外部存储失败语义有明确文档与关键测试。
- 新增复杂业务单据不需要修改 `EditPage` 核心接口。
- 非表单命令异常不会被静默吞掉或重复提示。
- 页签长期使用不会无限保留无上限的 DOM 和订阅资源。

### 9.6 前置依赖

阶段三和阶段四完成。

## 10. 阶段七：采购申请纵向验收

**状态：** `待实施`

### 10.1 目标

在批量增加业务模块前，使采购申请成为可复用到 ERP、MES 等后续系统的完整业务聚合样板。

### 10.2 问题依据

采购申请已具备基础纵向结构，但仍需用自动化规则和关键测试证明状态、事务、并发、权限、日志、缓存和前端页签形成稳定闭环。

### 10.3 修改与验收内容

- 保存、提交、删除和只读状态形成完整闭环。
- 所有修改命令携带并校验 `version`。
- 数据库更新同时校验 ID、当前状态和版本。
- 主单和明细在同一事务内保持一致。
- 操作日志、权限和缓存失效符合统一约定。
- 前端新增临时页签成功替换为真实单据页签。
- 保存后重新获取详情并回显数据库真实状态。
- 脏数据关闭保护覆盖新增和编辑页。
- 并发冲突具有自动化测试和明确用户提示。
- 根据验收结果形成新增业务聚合检查清单。

### 10.4 明确边界

- 验收完成前不批量扩展业务模块。
- 暂不实现审核、工作流、消息通知、采购订单转换和物料主数据。
- 不制作代码生成器或低代码引擎。
- 检查清单描述业务不变量和验证要求，不复制采购申请具体字段。

### 10.5 验收标准

- 阶段三的架构规则和阶段四的采购申请核心测试全部通过。
- 人工验收与自动化验证结论一致。
- 新增业务聚合可以依据检查清单复用架构路径，无需复制采购专属逻辑。
- 完成后才进入一次扩展一个业务聚合的受控业务扩展阶段。

### 10.6 前置依赖

阶段三至阶段六完成。
