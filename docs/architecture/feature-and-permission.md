# 功能与权限架构

本文档只定义 Domain/Application/Feature、菜单、页面和功能权限的稳定关联。数据范围与对象级访问见[数据权限设计](./data-permission.md)，高风险身份复核见[安全架构](./security.md)。

Feature（功能）是应用之下稳定的系统能力边界，用于组织页面、菜单和权限。系统目录层级统一为“领域 → 应用 → 功能 → 页面/菜单/权限”。一个功能可以包含多个页面和权限，也可以没有菜单；角色始终授予具体权限，Feature 本身不构成授权结果。

`Domain` 是领域的运行时目录，与 `sm.domain.{领域}` 及 `src/domain/{领域}` 的第一层编码保持一致，例如 `sys`、`scm`。应用通过 `domain_id` 归属一个领域，Feature 再通过应用归属领域；禁止另建与代码领域并行的“云”概念。

## 稳定身份与维护边界

- `feature_key` 使用 `/` 分隔的全局稳定业务键，例如 `sys/base/user`。
- 菜单 `number` 是可分享应用入口使用的稳定业务编码，创建后不可修改，在所属应用内必须唯一；数据库通过 `(app_id, number)` 唯一约束提供并发写入的最终保障。
- 系统内置功能的稳定键、所属应用、来源和默认值随代码版本通过新增 Flyway 迁移交付，禁止运行时扫描代码自动写库。
- 管理员可以维护自定义名称、排序、描述和目录可见性，不能修改系统功能稳定身份或凭配置创建不存在的代码能力。
- 默认名称、默认排序与管理员覆盖值分开保存；清空覆盖值即恢复系统默认。

## 关联规则

- 业务能力权限通过 `feature_id` 归属于功能，所属应用由功能推导；应用入口、应用分组等应用级权限通过 `app_id` 直接归属应用，二者必须且只能选择一种归属。
- 页面菜单必须关联功能，菜单入口权限必须属于同一功能；应用分组菜单可以不关联功能，但其入口权限必须是同一应用的应用级权限。
- 前端每个页面注册项必须显式声明 `featureKey`；同一功能的 LIST、EDIT、CUSTOM 页面共享同一 `featureKey`。
- `featureKey`、`componentKey`、菜单名称和权限编码职责独立，禁止在运行时通过权限编码前缀、菜单名称或组件路径推断功能归属。

## 菜单层级

- 分组菜单只能位于应用根级，不允许分组嵌套。
- 页面菜单可以直接位于应用根级，也可以归入同一应用下的分组，整体最多两层。
- 单页面或职责单一的应用优先使用根级页面；只有在分组能表达明确导航语义时才新建分组，避免为满足技术结构而创建空洞目录。
- 同一应用包含多个可独立演进、由不同维护者负责的能力簇时，必须按稳定业务语义建立根级分组；同一能力簇的配置、操作和记录页面归入同一分组。新增能力不得为了省略一次菜单迁移而散落为根级页面，也不得要求其他能力的维护者修改不属于其职责的菜单分支。

页面菜单必须显式声明目标类型：

- `INTERNAL_PAGE` 使用稳定 `componentKey` 进入前端页面注册白名单和工作台页签，内部路径与组件键均不能为空；
- `EXTERNAL_LINK` 使用绝对 HTTP/HTTPS 地址，不进入页面注册白名单，并通过 `NEW_TAB` 或 `IFRAME` 明确选择新浏览器标签页或工作台内嵌页；
- 分组菜单不允许携带页面目标、内部路径、组件键或外链字段；
- 两种页面目标都必须关联 Feature 和同一 Feature 下的入口权限，外链不绕过现有角色授权体系。

浏览器启动入口使用 `app={appNumber}&entry={menuNumber}` 定位应用和菜单，不使用数据库 ID。服务端用户菜单树必须返回菜单 `number`，前端只能在该用户实际可见的指定应用菜单树中匹配页面菜单；URL 参数不构成授权结果，也不能用于直接加载未授权的 `componentKey` 或外部链接。分组菜单不能作为启动入口。

iframe 外链受浏览器 CSP、混合内容规则以及目标站点 `X-Frame-Options`/CSP 限制；目标站点拒绝嵌入时不提供绕过机制。

## 安全与验证

Feature 只提供目录与归组语义。接口仍由具体权限码鉴权，高风险能力仍需公开 Service 复核真实管理员身份；功能可见性不能替代数据权限或对象级授权。质量门禁必须校验数据库功能目录、后端权限常量、菜单引用和前端页面注册的一致性。
