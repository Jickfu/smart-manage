# 组件适配与升级边界

[返回规范入口](./README.md)。本章是组件适配与升级边界的权威来源：以项目技术体系和业务需求为基础，在 Ant Design、ECharts 公开支持的能力内形成一致体验，允许合理的外观差异。目标是长期可维护的项目规范，验收不以外部参考的像素还原率衡量。

## 适配顺序

**A-10 必须。** 先使用原生能力，其次集中配置主题和组件，再考虑必要且有限的项目组合。公开接口是必要边界，不是无限定制的理由；即使使用公开接口，收益小而维护代价高的适配也应放弃。

| 层级 | 做法 | 默认处理 |
| --- | --- | --- |
| L0 原生能力 | 默认组件、内置图型、公开 props、布局与交互 | 优先使用；不因细微外观差异另造能力 |
| L1 集中配置 | 全局/组件 token、公开变体、图表 theme、palette、标准 option | 常规适配；复用现有配置入口，避免每页复制 |
| L2 有限扩展 | 当前版本明确支持的语义挂点/插槽、项目自有容器布局、薄组合及必要业务 render | 说明真实收益、影响和验证；复用原生状态与交互，不扩成第二套组件体系 |
| L3 深度定制 | 私有结构覆盖、依赖补丁、重写内置交互、以复杂自绘替代标准组件/图型 | 不能为外观复刻采用；真实业务能力不足时先评审需求和替代方案，不默认实施 |

普通 L0/L1 调整和授权范围内的 L2 实施仍走既有开发评审，无需逐项向负责人重复申请。需要改变产品行为、架构或引入实质性维护负担时，才把具体差异、替代方案和代价交给负责人决定。

## 两类库的适配入口

| 技术 | 优先配置 | 有条件使用 | 不作为视觉适配手段 |
| --- | --- | --- | --- |
| Ant Design | 现有 ConfigProvider 主题、全局/组件 token、公开 props 和变体 | 按锁定版本核实的 classNames 等语义挂点、公开插槽/render；样式集中在项目样式文件，仍遵守禁止 TSX 内联样式的现行规则 | 依赖内部节点顺序或深层 DOM、CSS-in-JS 哈希类、私有 rc-* 接口；修改依赖实现或重写选择/焦点/键盘协议 |
| ECharts | 已有 SmChart 生命周期、公开 theme/色板、标准 series/axis/legend/tooltip 等 option | 必要 formatter、公开事件与 action、真实业务需要的扩展；保持按需注册、数据语义与实例释放 | 改写内部 model/view/zrender 状态、拦截私有方法、渲染后改生成的 SVG/Canvas，或为了外观用复杂 graphic/custom 系列重画普通内置图型 |

官方能力依据：[Ant Design 主题定制](https://ant.design/docs/react/customize-theme/)、[ECharts 样式配置](https://echarts.apache.org/handbook/en/concepts/style/)。能力核对以项目实际锁定版本为准；线上文档可能对应更新版本。实现前按项目实际锁定版本核实 API、语义挂点及弃用情况，不因官网有新能力就假定本项目已具备，也不为此顺便升级依赖。

custom 系列、graphic、formatter、组件 render 等公开能力并非一概禁止。关键在于是否表达真实业务，还是为装饰性相似度承担了本来由库负责的绘制、布局、事件和可访问性。例如真实自定义业务图可单独评审；普通折线仅为精确控制每个节点而整体自绘不应采用。

## 何时停止适配

**A-11 必须。** 按业务价值、实现边界、影响范围和长期成本共同判断，不以“差几像素”或“公开 API 可实现”单独作决定。

| 判断 | 可常规实施 | 需要收敛或评审 | 应接受外观差异 |
| --- | --- | --- | --- |
| 收益 | 明确改善识别、密度、任务完成或统一性 | 主要是局部视觉精细度，用户价值不明显 | 只有截图更像，没有任务收益 |
| 接口与复杂度 | 少量稳定公开配置 | 多种 render/事件配合、组件组合明显变厚 | 依赖私有结构、补丁或重写原生协议 |
| 影响范围 | 现有集中入口，影响可解释 | 跨多组件/页面，需补大量例外 | 每页单独分支，或全局覆盖造成连锁修补 |
| 正确性 | 保留焦点、选择、加载、错误、缩放与原生语义 | 需要额外证明状态组合、性能或可访问性 | 为外观关闭校验、虚拟化等必要能力，或造成信息丢失 |
| 升级与退出 | 调整单一主题/公共入口即可回退 | 需版本专用处理且有明确退出条件 | 依赖固定内部 DOM、永久补丁或无法独立移除 |

L0/L1 若配置开始膨胀、出现多处互相抵消的覆盖，同样应停止叠加。一次适配需要反复修补其它页面，通常说明设计目标或实现位置应调整；优先回到原生表现、调整页面布局或降低视觉要求。

不设统一的“允许改多少行”或“必须还原多少百分比”，这些数字不能衡量风险。评审记录实际配置/封装位置、受影响组件与页面、版本耦合、需要新增的状态验证和回退方式，成本随这些证据判断。

## 保留什么与允许什么差异

| 内容 | 项目目标 | 边界内的取舍 |
| --- | --- | --- |
| 业务事实、权限、关键数值和风险行为 | 正确、完整、可信 | 不以库限制或外观为由弱化；可调整布局、入口和任务流程，按业务决定 |
| 品牌、语义色、文字层级、密度和空间 | 在公开主题及布局能力内保持整体一致 | 采用最接近且稳定的配置，不为精确数字破坏原生布局 |
| 下拉、日期、树与选择交互 | 原生语义与项目业务契约一致 | 接受弹出细节、动画和内部排版差异，不重做组件内部实现 |
| 图表 | 数据表达准确、主题与图例等整体协调 | 接受自动刻度、标签避让、节点和提示定位的合理差异，不接管整个布局算法 |
| 图标与插画 | 含义清楚、同组一致 | 不重绘整套现有图标只为几何完全一致 |
| 阴影、边线、圆角和动效 | 区分层级、状态和反馈 | 组件支持的稳定表达优先；细节参数不是逐像素硬指标 |

例如，关键金额显示不下时先调列宽、布局或所属区域滚动，不另造表格引擎；图表轴标签过密时调整图幅、间隔或表达方式，不修改 ECharts 内部排版；日期面板结构不同但任务正常时保留原生面板。

## 禁止做法与存量处理

**A-12 必须。** 不为外观一致性 fork、补丁修改或复制 Ant Design/ECharts 源码，不修改 node_modules，不使用 monkey patch，不绕过公开组件协议访问私有内部状态。不得靠不断叠加深层选择器、!important 或定时测量/回写 DOM 掩盖不合适的设计目标。

不为一次视觉差异新增通用适配框架、大量布尔开关或业务专用公共分支。已有项目封装承担业务契约与生命周期时继续复用，例如 RefSelector、AppModal、EditableDetailTable、SmChart；不能把“保持原生”误解为拆掉项目已有有效能力。

修改存量 CSS 时按实际影响范围评估，不因存在覆盖就扩大清理范围。修改相关能力时检查存量覆盖：优先迁到公开 token/语义挂点，仍有必要的历史覆盖记录作用域、原因、升级验证和退出条件；不因已有一个内部选择器就继续扩大这种方式。真实上游缺陷或紧急业务修复按专项问题评审，不能借用“主题适配”名义长期保留。

## 差异记录与升级验收

**A-13 必须。** 公开 API 不保证跨版本永不变化。新增适配记录其依据与作用域；依赖升级时按实际变更检查受影响的公开 API、主题和项目封装。测试与构建的命令和触发条件仍只由[质量验证](../development/verification.md)维护。

| 记录项 | 应说明 |
| --- | --- |
| 设计目标与收益 | 解决哪个用户任务或一致性问题 |
| 适配方式 | L0/L1/L2、公开入口、当前版本及集中配置位置 |
| 接受的差异 | 哪些外观或布局细节采用原生行为及原因 |
| 影响与成本 | 组件/页面、状态、性能、可访问性与版本耦合 |
| 验证与退出 | 对应证据、如何回退、何时删除临时处理 |

常规升级先核对变更说明与弃用项，再验证被影响的表单、表格、选择器、弹层、焦点/键盘、换肤，以及图表数据、标签、提示、尺寸变化与释放。不能承诺只更新版本号即可升级，也不能为了免于调整长期锁死版本。

接受合理差异是正式设计结果：在设计稿或差异记录中说明即可，不把它当作必须通过更多特殊处理消除的缺陷。
